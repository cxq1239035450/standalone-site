# 性能与缓存：实施及部署手册

适用版本：本次性能优化改动。设计依据见 [完整方案](./performance-and-cache-plan.md)。

## 已落地的行为

- CMS 本地图片和视频按实际文件内容生成 SHA-256 地址：`/assets/media/<hash>.<ext>`。同文件跨页面/语言复用；修改说明和翻译不改变地址，替换文件产生新地址。
- 旧原文件及旧不可变版本保留。快照在同一磁盘以临时文件写完后原子发布，不会将未写完的文件交给访客。
- 指纹资源返回一年 immutable 缓存、ETag、HEAD、视频 Range/206；错误不强缓存。Next 图片优化容量上限500MB，最低TTL4小时，源文件已不可变时实际缓存期可更长。
- 普通图片默认质量75，修正 sizes，首屏关键图使用高优先级，屏外图懒加载；移除每张图都带的大段通用base64占位。
- 统一 Payload 与 Next 使用的 Sharp 为锁定的0.35.3，避免Windows进程先加载0.34.2、再加载0.35.3时出现原生模块冲突并静默回退原图；通过pnpm override保持同一版本。
- 普通视频不自动播放，使用浏览器原生播放控件、`preload=none`和固定宽高比。可通过组件参数指定封面；显式背景模式仅在可见且非节流/减少动画偏好时自动播放。
- 公开翻译正文使用有容量限制的5分钟内存缓存。每次先实时查询语言权限、公开结果集及版本号；版本不匹配立即读取新正文。共享库存和价格、关联内容仍实时读取，预览与登录上下文绕过正文缓存。
- 列表共享主体每100条一批读取，替代逐条查询；SEO公开内容按100条分页处理。导航/页脚使用请求内去重，避免把预览上下文放入跨请求缓存。
- 后台“媒体文件”列表增加“性能与缓存”面板，查看文件数量、空间、处理和正文命中计数；状态刷新带loading，策略详情使用现有Radix弹窗。
- Nginx模板增加文本压缩和指纹媒体静态交付；页面、后台、通用API不做全站代理强缓存。

本次选择“实时版本校验”替代方案中的异步失效队列：缓存不保存公开列表结果，也不缓存权限。各实例在下一次读取时自行发现变更，无须先引入Redis或新任务表。失效任务延迟不会让旧内容继续出现在新请求中。

## 环境配置

```dotenv
# 默认使用原有媒体目录；生产通常已配置或通过软链接共享
MEDIA_DIR=/opt/standalone-site/shared/media
# 可选，默认 MEDIA_DIR/.immutable；须与 Nginx alias 一致
MEDIA_CACHE_DIR=/opt/standalone-site/shared/media/.immutable
# 默认启用；0 为应急关闭（更改后重启应用）
MEDIA_IMMUTABLE_CACHE=1
PUBLIC_CONTENT_CACHE=1
```

媒体目录和缓存目录必须允许应用用户读取/写入。`.immutable`内对象文件不可覆盖；`.index`仅存文件签名与URL，可重新生成，让预热效果跨进程/重启复用。不得把私有附件接入本模块。关闭本地存储的云存储适配器会保留其原URL，不尝试读取本地文件。

当前模块支持 JPEG、PNG、WebP、AVIF、GIF、MP4、WebM、Ogg视频。SVG及其他格式保留原有交付方式，不进入公开不可变快照。缓存不可用时回退原URL并记录告警，后台不会因为缓存目录故障而无法读取记录。

## 迁移：无需修改数据库表

此实现不新增数据库字段、不修改媒体ID及关系，也不改写已有翻译。因此**没有需要运行的SQL迁移**，避免不同分支出现额外数据库结构依赖；补充的是幂等、可预检查的文件缓存迁移。

先备份媒体目录。使用与生产服务一致的环境变量和应用用户执行：

```sh
# 仅检查数量和原始字节数，不写文件
pnpm migrate:media-cache

# 为现有文件和图片变体生成快照及加速索引
pnpm migrate:media-cache --apply

# 可再次执行；已有内容地址复用，原文件和数据库都保持原样
pnpm migrate:media-cache --apply
```

脚本只处理媒体目录根部的普通文件，不遍历软链接和缓存目录。失败输出对应文件名并以非零状态退出；补齐文件/权限后可重跑。每个文件流式处理，不一次把全部视频读入内存。原始媒体与快照可能占用接近两倍空间，预检查后确认可用容量。

新上传文件在读取时自动生成快照，无须每次手动迁移。生产可在发布前预热历史媒体，减少首次访问的文件处理开销。

## 发布步骤

1. 获取代码与锁文件，保留生产环境密钥和现有媒体共享目录。
2. 确认当前分支已完成此前多语言、SEO、邮件的数据库迁移；本次不代替那些迁移。
3. `pnpm install --frozen-lockfile`；设置媒体共享路径和两个缓存开关。
4. 执行文件缓存dry-run、检查磁盘容量、执行`--apply`。
5. `pnpm build`，在新release中启动并验证公开页面、匿名权限和后台。
6. 合并 `deploy/nginx.conf` 中的增量规则到当前实际站点配置；不要直接覆盖已有域名、HTTPS和其他服务规则。
7. 核对指纹资源alias实际指向共享`.immutable`目录，运行 `nginx -t`，通过后平滑加载。
8. 普通刷新和关闭标签页后重进验证浏览器缓存；校验视频播放、拖动、后台替换文件、撤回翻译。

不配置Nginx静态交付时，Next的`/assets/media/[name]`接口仍提供完整缓存/Range能力；可以先上线应用，再独立启用Nginx规则。CDN暂不必接入，避免一次增加多个无法定位的缓存层。

部署不要共享整个`.next`目录。快照通过共享媒体目录跨发布保留；Next优化图片的本地缓存按当前release管理，是否进一步共享图片变体缓存应单独验证框架版本兼容性。

本次需要Node.js >=20.9，推荐沿用部署说明中的Node.js 22。务必同步`package.json`和`pnpm-lock.yaml`，不要只复制图片组件。若原地更新且曾缓存过“压缩失败回退原图”的结果，停服务后将该release的`.next/cache/images`重命名备份，再启动生成新缓存；不要删除整个构建目录或媒体目录。新release通常无需这一步。Sharp的原生依赖与平台要求见[官方安装说明](https://sharp.pixelplumbing.com/install/)。

## 读取与管理接口

- `GET/HEAD /assets/media/<hash>.<ext>`：只交付白名单公开类型，不查数据库，不接受任意路径。
- `GET /api/performance/status`：仅登录用户可读，`private, no-store`。文件数量/空间来自磁盘；命中、处理计数仅代表本进程，重启后归零，不宣称浏览器/CDN命中率。
- 缓存面板的“刷新状态”只重新读取状态；不会清除其他用户浏览器的文件。

后台没有“清空所有媒体”按钮：旧版本可能仍被已打开页面、浏览器缓存或回滚版本引用。只有经过引用审计和保留期核对后才能单独设计清理任务。

## 故障与回滚

| 现象 | 检查与处理 |
| --- | --- |
| 指纹文件404 | 核对Nginx alias、MEDIA_CACHE_DIR和共享卷；先让该路径走Next接口进行对照 |
| 文件处理失败计数增加 | 检查源文件是否存在、目录权限、磁盘空间；不要删除原文件 |
| 后台没有统计 | 确认登录和状态接口返回；无CDN指标属于当前正常边界 |
| 新图片没有变化 | 确认文件字节实际改变且前台src换了hash；仅改说明不应换hash |
| 需要关闭正文缓存 | `PUBLIC_CONTENT_CACHE=0`并重启；读取继续使用原有发布校验 |
| 需要关闭媒体URL转换 | `MEDIA_IMMUTABLE_CACHE=0`并重启；保留指纹路由/Nginx和旧快照以服务已打开页面 |
| 回滚旧应用 | 切回旧release；原数据库和原媒体仍可用。保留新指纹静态路径，不删共享目录 |

强制刷新、浏览器缓存被清理、不同图片尺寸、尚未缓存的视频片段仍会产生传输。视频Range部分缓存不等于全片离线保存。
